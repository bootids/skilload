# Establish the skilload product and architecture baseline

This ExecPlan defines the first authoritative documentation baseline for skilload. When the delivery is complete, a newcomer will be able to understand the CLI MVP's promised behavior, the system boundaries that constrain later implementation, and the technical design chosen to satisfy those promises without relying on chat history or the original handoff. The result is observable by reading the versioned behavior specifications, following their acceptance clauses, and checking that `ARCHITECTURE.md` and the design documents consistently trace back to those behaviors.

This ExecPlan is a living document. As work proceeds, the `Progress`, `Surprises & Discoveries`, `Decision Log`, `Outcomes & Retrospective`, and `Review Conversation Log` sections must be kept current. It must be maintained in accordance with `docs/PLANS.md`.

Revision 1 acceptance for this documentation delivery is that every ID appears exactly once as a definition heading in its stated product specification; each definition contains a normative behavior statement, explicit acceptance examples or conditions, and status/scope metadata; all confirmed decisions in `Context and Orientation` map to at least one ID; and no architecture or design document changes the user-visible semantics defined by those IDs. Later implementation Plans must select the exact IDs and revisions they implement and provide runtime or test evidence. This Plan's own acceptance is documentation integrity, not executable product behavior.

## Design and Architecture Inputs

`ARCHITECTURE.md` must become the short, authoritative map of repository structure, dependency direction, ownership boundaries, and cross-cutting invariants. It must identify a Rust Cargo workspace with a core/application library crate and a CLI binary crate, even though this delivery does not create those directories. Product specifications remain authoritative for behavior; the architecture must link to them rather than restating acceptance in altered language.

The design documentation must explain the chosen implementation approach and rationale in five focused files: `docs/design-docs/application-and-persistence.md`, `docs/design-docs/github-resolution-and-integrity.md`, `docs/design-docs/deployment-transactions-and-recovery.md`, `docs/design-docs/agent-adapters-and-manager.md`, and `docs/design-docs/cli-json-and-release.md`. Reusable external facts about native Agent Skill discovery and the open Skill-name contract, GitHub repository identity/authentication plus Git helper/SSH/repository-selection and bounded pack-receive constraints, the observed `npx skills` installation model, pinned Unicode 15.1 normalization/case-fold inputs, operating-system script/interpreter dispatch, and SQLite backup/WAL/integrity/salvage behavior must be captured separately under `docs/references/` with primary sources and dates. Design documents may cite those references but cannot turn environment facts into product promises.

The dependency direction is inward: CLI parsing and Agent/Git/SQLite/filesystem adapters may call application services; application services coordinate domain operations and ports; domain rules do not import CLI, database, Git process, Agent-specific, or presentation code. All mutating commands use a single application layer, so future TUI and Web adapters can be added without bypassing policy or persistence ownership. No future UI code or stub implementation is part of this delivery.

## Purpose / Big Picture

skilload is a local, single-binary manager for GitHub-hosted Agent Skills. Its first useful release lets one developer maintain a searchable local Library, approve exact sources, pin reproducible workspace and global deployments, and make selected Skills discoverable by Claude Code and Codex through their native directories. It also installs a built-in manager Skill so either Agent can manage skilload by invoking the stable JSON CLI. GitHub remains the source of Skill content; durable local state contains references, trust, metadata, desired state, and integrity records, while removable content lives only in cache.

The repository currently has governance documents but no product specification, technical design, implementation, or nonempty architecture. This P0 delivery turns the fully settled product design into authoritative repository documents. It deliberately stops before code so later ExecPlans can select stable behavior revisions rather than reconstructing product intent.

## Surprises & Discoveries

- Observation: the original handoff described wrapper-launched Agents, temporary runtime mounts, Collections, TUI, and Web as initial scope, but the completed product interview explicitly removed all of those from the 0.1 CLI MVP.
  Evidence: the settled command surface has no `claude`, `codex`, `tui`, `web`, `collection`, or `init` command and instead uses persistent workspace/global native Skill links plus a separately installed manager Skill.
- Observation: the checked-in repository contains only governance scaffolding; `ARCHITECTURE.md` is empty and both product and design directories contain only `.gitkeep` files.
  Evidence: `git ls-files` on 2026-08-18 listed no product specification, design document, reference, source manifest, or implementation file.
- Observation: current Codex documentation names `$HOME/.agents/skills` as the personal Skill root, while current Codex source still reads `$CODEX_HOME/skills` as a deprecated compatibility location.
  Evidence: `docs/references/claude-and-codex-skill-discovery.md` cites the official Skill page and Codex commit `5ee6baee2fcc0b6ffd413d9611f5538dad40d0f2`, whose `host_roots.rs` loads both roots and labels the config-root location deprecated.
- Observation: current Claude and Codex releases can detect many Skill changes without restart, but both retain restart qualifications and Codex symlink reload behavior has varied.
  Evidence: the official Agent Skill pages referenced on 2026-08-18 describe live detection and recommend restart in qualifying cases; the settled next-launch guarantee remains conservative and valid.
- Observation: npm `skills` 1.5.22 recursively copies full Skill directories and uses a canonical `.agents/skills` copy plus Agent-specific links, but its lock and extraction choices do not meet skilload's identity/integrity contract.
  Evidence: inspected commit `c6f69c631292444cc541ac6d91e2226b0ff247da` stores a GitHub folder tree SHA rather than skilload's repository-ID/commit/canonical-digest tuple, dereferences symlinks, leaves LFS pointers, and does not initialize submodules.
- Observation: the traceability pass found the confirmed Apache-2.0 continuity promise only in Plan context and release-design prose, with no authoritative product behavior ID.
  Evidence: before `SKL-PROD-007` was added, the product-specification inventory ended at `SKL-PROD-006` even though the Context and release archive design required the repository license to continue and ship with artifacts.
- Observation: first-add pair atomicity was phrased as an impossible raw failpoint observation even though the surrounding baseline already uses journal recovery for multi-file and multi-directory changes.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z-2tN` compared `SKL-WSP-002` with `SKL-WSP-006`, `SKL-WSP-016`, and the two-rename sequence in `docs/design-docs/deployment-transactions-and-recovery.md`.
- Observation: Git resolves a linked worktree's exclude file outside the workspace because its `.git` entry is a regular indirection file.
  Evidence: a local Git 2.50.1 fixture observed an ordinary worktree `.git` directory and relative `.git/info/exclude`, but a linked worktree `.git` regular file and an absolute common-repository `info/exclude` result from `git rev-parse --git-path info/exclude`.
- Observation: Revision 1 named source/discovery limits and XDG fallbacks without enough values or validation rules for independent implementations to agree.
  Evidence: review threads `PRRT_kwDOT7YN2s6Z-2tW` and `PRRT_kwDOT7YN2s6Z-2tX` identified the missing numeric ceilings, override lifetime, and absolute-path handling.
- Observation: the cache design showed 536,870,912 bytes only as an example configuration and named an operation-specific override without making either user-visible contract authoritative.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z_IxA` compared `SKL-CACHE-003` with `docs/design-docs/application-and-persistence.md` and `docs/design-docs/cli-json-and-release.md`.
- Observation: the product profile identity was already `(Agent, canonical global root)`, but the Agent design instead mapped a broader environment fingerprint that includes auxiliary Codex roots to `profile_id`.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z_IxD` showed that changing only `CODEX_HOME` could allocate competing ownership for the unchanged `$HOME/.agents/skills` target.
- Observation: the all-target accessibility rule made a permanently unavailable global profile impossible to uninstall while also allowing it to block every future shared-pin change.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z_IxG` found no detach route in the canonical command surface, cache clear, Trust revocation, Library removal, or doctor behavior.
- Observation: no permission bit or content-addressed path can prevent a process running as the same user from modifying bytes behind a native symlink after skilload verifies it.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z_IxH` reconciled the no-wrapper architecture and direct Agent symlink reads with the previous absolute "never served" wording in `SKL-CACHE-005`.
- Observation: the canonical source display used unescaped `@` as the path/ref separator even though both Git paths and refs may contain that byte.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z_i7c` supplied two distinct path/ref tuples that serialized to the same text and could therefore collide in Trust and portable state.
- Observation: resolving only a nested workspace's effective exclude file is insufficient because slash-containing Git-ignore patterns are evaluated from the worktree root.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z_i7d` showed that `.skilload/state/deployments.json` does not match `packages/app/.skilload/state/deployments.json` for a workspace below the worktree root.

  Evidence: review thread `PRRT_kwDOT7YN2s6Z_i7h` identified 32-bit, 64-bit, and minimal-width encodings as all compatible with the previous prose.
- Observation: a safely fetched repository can still attack a Trust decision if its description, paths, or warnings reach a terminal as raw control sequences.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z_i7l` traced ANSI/OSC and carriage-return injection through the first-approval human preview before Trust exists.
- Observation: validating each XDG root independently does not preserve state separation when effective application roots are equal, nested, or symlink aliases.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z_i7n` showed that equal data/cache homes put the durable database beneath the same application root that cache clear treats as removable.
- Observation: workspace ownership repeated the global-profile identity defect by treating auxiliary environment observations as identity even when the project target root stayed fixed.
  Evidence: review thread `PRRT_kwDOT7YN2s6Z_i7o` showed that a `CODEX_HOME`-only change could allocate a second owner for unchanged `<workspace>/.agents/skills` links.

  Evidence: review thread `PRRT_kwDOT7YN2s6Z_i7p` showed that conforming implementations could disagree on `Review`/`review` and composed/decomposed Unicode across mutation, import/export, and search.
- Observation: storing only short Git ref text loses whether a mutable source intended a branch or tag when both namespaces contain the same name.
  Evidence: review thread `PRRT_kwDOT7YN2s6aAPmW` showed that `refs/heads/release` and `refs/tags/release` can resolve to different commits while both previously serialized as `@release`.
- Observation: JSON strings cannot carry the invalid UTF-8 bytes that supported Unix filesystem paths and the terminal-safety fixture permit.
  Evidence: review thread `PRRT_kwDOT7YN2s6aAPmY` found that the CLI design promised a lossless path representation without defining its API-v1 shape or scope.
- Observation: Agent executable overrides were configuration examples rather than an authoritative key/type/default contract.
  Evidence: review thread `PRRT_kwDOT7YN2s6aAPma` found that callers could not portably configure the fallback promised by Agent preflight.
- Observation: canonical-path ownership gives a moved workspace a new identity but provided no transition from its old durable registration and moved local manifest.
  Evidence: review thread `PRRT_kwDOT7YN2s6aAPmb` traced a normal repository rename to stranded links, an inaccessible old workspace record, and blocked cache cleanup.
- Observation: resolving an Agent executable through an empty or relative PATH component can execute repository-controlled code before the inert-source boundary applies.
  Evidence: review thread `PRRT_kwDOT7YN2s6aAPme` showed that canonicalizing after lookup is too late when a workspace contains a malicious `claude` or `codex` binary.
- Observation: resolving a trusted Git executable does not constrain the SSH program that Git starts for an SSH remote.
  Evidence: review thread `PRRT_kwDOT7YN2s6aA2iR` and a local Git 2.50.1 fixture showed `git ls-remote` executing a workspace `ssh` selected through PATH; an application-owned `GIT_SSH_COMMAND` instead reached only the revalidated safe fixture.
- Observation: unconditional Agent-executable preflight can strand exact owned links and manager copies after the corresponding Agent is uninstalled.
  Evidence: review thread `PRRT_kwDOT7YN2s6aA2ia` traced empty workspace sync, normal global uninstall, and manager uninstall through executable-dependent preflight even though their exact roots and ownership evidence can remain accessible.
- Observation: the verified Skill name was a filesystem target and comparison key without a Revision 1 grammar or normalization rule.
  Evidence: review thread `PRRT_kwDOT7YN2s6aA2if` showed that implementations could disagree on accepted lengths, case, separators, Unicode, and duplicate identity despite both native Agents using the open Agent Skills format.
- Observation: Agent-root formulas interpolated environment values without rejecting empty or relative paths.
  Evidence: review thread `PRRT_kwDOT7YN2s6aA2ii` showed that `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or required `HOME` could otherwise derive roots beneath CWD independently of the already-safe skilload XDG algorithm.
- Observation: Git exclusion does not prevent a user from force-adding the machine-local deployment manifest.
  Evidence: review thread `PRRT_kwDOT7YN2s6aA2im` and a local literal-path fixture showed `git add -f` making the manifest tracked while leaving ordinary sync/recovery able to rewrite it unless every mutation checks the index.
- Observation: semantic YAML validation alone cannot bound resource use while reading a hostile cloned workspace document.
  Evidence: review thread `PRRT_kwDOT7YN2s6aA2iq` identified missing byte, record, node, depth, scalar, alias, tag, and duplicate-key gates before `.skilload.yaml` model construction.
- Observation: invoking a trusted absolute Git binary does not constrain Git's core-helper lookup when `GIT_EXEC_PATH` survives.
  Evidence: review thread `PRRT_kwDOT7YN2s6aB8tL`, official Git invocation documentation, and a local Git 2.50.1 fixture showed `/usr/bin/git` executing a marker `git-remote-https` from the inherited directory; explicit `--exec-path` selected only the fixed safe fixture.
- Observation: the source-migration design's "known reference records" wording crossed the product's separate workspace migration boundary.
  Evidence: review thread `PRRT_kwDOT7YN2s6aB8tT` traced an early workspace ownership-row rewrite to lost manifest/database equality and blocked later `workspace migrate-source` preflight.
- Observation: atomic Library import does not itself bound parser/model allocation or persisted metadata.
  Evidence: review thread `PRRT_kwDOT7YN2s6aB8tW` identified unlimited input bytes, entries, values, depth, scalar tokens, alias/category/note lengths, and tags before `ImportPlan` construction.
- Observation: a literal tracked-file query can inspect the wrong index when caller Git repository variables survive.
  Evidence: review thread `PRRT_kwDOT7YN2s6aB8tZ`, official Git repository-environment documentation, and a local Git 2.50.1 fixture showed an alternate empty `GIT_INDEX_FILE` hiding a tracked manifest while explicit real worktree/Git-directory/index binding found it.
- Observation: the seventh review pass exposed one materially incomplete acceptance area and seven adjacent determinism/resource/recovery gaps rather than ordinary isolated wording defects.
  Evidence: thread `PRRT_kwDOT7YN2s6aC9WY` found no required API-v1 payload schema for most of the 50 command leaves, while threads RC-031 through RC-036 and RC-038 found unbounded Agent inputs/fetches, host-dependent path collisions, incompatible quarantine/quota behavior, undefined root naming, no actionable database recovery procedure, and indirect interpreter execution.

## Context and Orientation

The repository root is `/Users/yangxuhui/Projects/Products/skilload` in the current environment. `AGENTS.md` defines documentation precedence and Plan lifecycle. `docs/PLANS.md` defines this Plan's required format and state transitions. `ARCHITECTURE.md` exists but is empty. `docs/product-specs/`, `docs/design-docs/`, and `docs/references/` contain only `.gitkeep` placeholders. There is no application code, Cargo manifest, test runner, or release workflow.

The authoritative product meaning to encode is the following.

skilload's primary wedge is reproducible, workspace-scoped Skill loading for a developer who uses both local Claude Code and local Codex CLI. A Skill is a directory rooted at a required `SKILL.md`. GitHub is the only external content source in the 0.1 MVP. skilload stores no durable copy of external Skill files; it stores them only in a removable cache whose objects skilload manages as immutable. The 0.1 release is CLI-only. It excludes a wrapper or Agent launcher, runtime leases, Collections, TUI, Web/HTTP service, daemon, MCP server, marketplace, compiler, semantic conversion, embeddings, cloud sync, remote Agent sessions, shortcuts, and `init`. Future TUI and Web releases remain possible in later 0.x minors, and 1.0 is reserved until both exist and have passed stability testing. Development artifacts use 0.0.x; the complete CLI MVP is 0.1.0; Homebrew stable starts at 0.1.0. The supported hosts are macOS and Linux on arm64 and x86_64.

A source is an exact structured owner/repository/Skill-path/ref-intent tuple on `github.com`, bound after validation to GitHub's immutable numeric repository ID. Its portable text uses lowercase owner/repository plus injective uppercase UTF-8 percent encoding for non-unreserved path/ref bytes, including literal `%`, `#`, and `@`, so exactly one literal `#` and `@` delimit the tuple without Unicode-normalizing Git paths. A branch is stored as `refs/heads/...`, a tag as `refs/tags/...`, and a commit as lowercase full SHA; short input matching both mutable namespaces fails with both candidates rather than inheriting Git precedence. Accepted input includes GitHub HTTPS tree/blob URLs, GitHub SSH repository URLs, and `owner/repo` shorthand. Missing refs resolve to the fully qualified default branch. SHA sources are already immutable and update reports `already_immutable`. A repository URL without an exact path is scanned for candidate `SKILL.md` roots. One candidate can be selected automatically; multiple candidates require explicit selection and JSON returns the candidate set. A root `SKILL.md` makes the whole repository the Skill directory, excluding `.git`.

The full Skill directory is materialized. Its bounded UTF-8 frontmatter requires a 1-64-byte lowercase ASCII `name` matching `^[a-z0-9]+(?:-[a-z0-9]+)*$`, exact byte equality with the logical source directory, and a nonempty description of at most 1,024 Unicode scalar values; names are never trimmed, case-folded, or Unicode-normalized. For a repository-root Skill only, the logical segment comes from fresh GitHub metadata `name`: lowercase ASCII, collapse each maximal `.`, `_`, or `-` run to one hyphen, strip edge hyphens, preserve original display spelling separately, and reject an empty or over-64-byte result. Frontmatter validation stops before a full model on the 65,537th byte, 513th node, ninth container level, 4,097th scalar byte, aliases/anchors/tags, duplicate keys, or non-string keys. Regular bytes and executable bits are preserved. Only relative symlinks whose resolved targets stay within that Skill directory are permitted. Every path is valid UTF-8 and receives the pinned Unicode-15.1 `skilload-path-key-v1` NFD/full-default-case-fold/NFD key; distinct raw paths with one key fail portably, while exclusive target materialization rejects any additional host-filesystem alias without changing the original path/digest/lock. Submodules and unmaterialized Git LFS pointers are rejected. Repository-only discovery visits at most 100,000 Git entries and returns at most 256 valid candidates; an exact Skill path bypasses discovery. A selected Skill defaults to at most 2,000 regular-file/symlink entries and 52,428,800 bytes. Explicit numeric file/byte ceilings may raise those selected-Skill limits for one exact request, are confirmation-bound, and are not persisted. The lock integrity is a canonical SHA-256 tree hash over original relative path bytes, regular-file bytes, executable bits, and allowed symlink targets; version 1 assigns fixed type/executable bytes and encodes every following-byte length as exactly eight unsigned big-endian bytes. It is recorded with repository ID, commit, and verified Skill name. Reproducibility is conditional: a lock can restore exact content while the commit remains available from GitHub or a previously verified cache entry exists. A rename or transfer of the same numeric repository ID requires explicit source migration; only the owner/repository spelling changes in that operation, while path or ref changes create a new source and new Trust decision.

Fetching is data-only: skilload invokes system Git but never executes repository code, scripts, or hooks. Git, optional `gh`, and the SSH client used by Git are discovered only through nonempty absolute PATH directories; any candidate, symlink target, or supported script interpreter in the current project/worktree or skilload source/cache roots is rejected before execution. Native executables or bounded direct/`/usr/bin/env <basename>` script chains are resolved to explicit argv without a shell, limited to four script identities, supplied only a resolver-built safe PATH, and completely revalidated before spawn. Every Git child starts from an allowlist with no caller-provided `GIT_*` name, fixes the cleanly discovered absolute Git exec directory through `--exec-path`, and adds only application-owned settings; helper, dynamic-config, repository, index, object, and SSH selectors therefore cannot survive from the caller. An SSH attempt revalidates the independently resolved SSH launch and gives Git only an application-owned shell-quoted command with fixed noninteractive options and variant. Exact-ref receive is independently capped per source at 268,435,456 pack bytes, 250,000 declared objects, and 120 seconds, and per invocation at 1,073,741,824 bytes, 1,000,000 objects, and 600 seconds across fallback/retry. A supervised receiver checks bytes before forwarding and the pack header before object-table allocation, passes the byte cap to the validated indexer, terminates/waits for process groups, removes failed staging, and forbids an ordinary unbounded porcelain fetch. Credentials are neither prompted for nor stored. Public repository metadata may be queried without authentication subject to GitHub limits. Private source validation requires authenticated GitHub REST or GraphQL metadata through `GH_TOKEN`, `GITHUB_TOKEN`, or authenticated `gh`; SSH Git access alone cannot establish the numeric repository identity. Commit signatures are not required.

Trust is local durable authorization for one exact namespace-preserving source and immutable repository ID. The first direct GitHub add to either Library or workspace may fetch into a safe temporary area, validate content, and show source, repository ID, commit, verified name, description, file count, total bytes, and warnings before approval. Every repository/path/environment/user field in human output uses an injective quoted encoding that exposes rather than executes terminal controls, invalid bytes, and bidirectional formatting; renderer layout/styling is the only raw control source. JSON standards-escapes valid logical strings, while every host filesystem path always uses `{ display, bytes_base64 }` so even invalid UTF-8 bytes round-trip without a field-type change. Trust is separate from Library membership. A cloned `.skilload.yaml` never grants local Trust, and first Trust must be validated online or matched to a previously verified local record. In JSON mode there is no prompt; confirmation uses a short-lived single-use token bound to the action and complete preview plan, including all sources, repositories, commits, targets, overrides, conflicts, database revision, and workspace digest; any relevant state drift invalidates it. Revoking Trust preserves existing managed links but blocks future update, sync, cache-miss restoration, and recovery for that source; removal and uninstall remain allowed.

The global Library stores stable source identity plus optional unique alias, one optional free-text category, normalized deduplicated tags, a free-text note, and derived name/description/repository metadata. Alias/category each stop at 256 scalars and 1,024 UTF-8 bytes, note stops at 4,096 scalars and 16,384 bytes, and one entry has at most 64 distinct tag keys. Tag version 1 trims Unicode-15.1 White_Space, stores the first NFC display spelling, deduplicates/removes/sorts through its locale-independent full-default-case-folded NFC key, rejects control/empty/over-64-scalar/over-256-byte values, and indexes both display and key. Adding an exact already-known source is idempotent `already_exists` and does not refresh metadata. First GitHub add can establish Trust after approval. List and search are offline and use embedded SQLite FTS5 across name, description, alias, tags, category, note, and repository. Refresh is explicit and does not change workspace locks. Removing Library metadata does not revoke Trust, delete cache, remove global deployment, or alter workspace files, and it reports known references. Export/import uses versioned JSON and carries Library metadata only, never Trust, global desired state, local paths, or cache content. Before deserialization/planning, import streams at most 67,108,864 bytes, 10,000 entries, 1,000,000 values, eight container levels, 1,048,576 bytes per string, and 128 bytes per number while rejecting duplicate keys. Import is atomic and supports dry-run; existing sources are kept by default, alias conflicts fail, and explicit replace affects metadata only. The target is at least 10,000 entries.

There is no workspace `init`. A workspace-dependent command operates only when the current working directory itself contains `.skilload.yaml`; there is no upward search. Global Library, Trust, cache, manager, and global-deployment commands work from any directory. The first successful `workspace add` commits `.skilload.yaml` and `.skilload.lock` as one journaled pair, while an ordinarily returned failure leaves neither. An interruption between renames may expose a transitional one-file state until mandatory recovery restores absence or completes both files. Adding inside a child of an existing workspace is refused unless `--allow-nested` is explicit. A workspace need not be a Git repository.

`.skilload.yaml` contains normalized sources only, with no Library IDs, Agent targets, Trust, or machine paths. `.skilload.lock` contains deterministic resolved commits, repository identities, verified names, and integrity data. Each is one UTF-8 YAML document capped at 1,048,576 bytes, 200 records, 4,096 scalar/mapping/sequence nodes, eight container levels, and 4,096 UTF-8 bytes per scalar. A non-expanding event pass rejects aliases, anchors, explicit tags, directives, multiple documents, duplicate keys, and non-string keys before a complete model, source resolution, or persistent allocation. Both documents are committed and machine-managed; comments and hand formatting are not preserved. `workspace add` and `workspace remove` update config and lock as a recoverable pair but do not write Agent Skill directories. A direct-source add may establish Trust but does not add Library membership. Removing the final Skill leaves empty config and lock files.

`workspace lock` reconciles configuration and lock: it preserves unchanged source commits, resolves new sources, and removes stale entries without advancing existing mutable refs. `workspace update` advances mutable refs and, with no selector, is an atomic all-source batch. `workspace pin` may choose a historical commit while retaining the mutable source so a future update can advance it. A SHA source never advances. Duplicate verified Skill names within a workspace are hard failures with no override. An upstream name change requires explicit acknowledgement of the rename and preflight for conflicts and the reserved manager name. Source rename/transfer migration and schema-format migration are explicit; `source migrate` changes Library, Trust, and global records while reporting workspaces read-only, and only journaled `workspace migrate-source` changes workspace config/lock plus matching ownership. Read, status, and sync never silently rewrite schema or source spelling.

`workspace sync --agent ...` requires one or more explicit Agents and deploys the entire workspace set to each selected Agent, all-or-nothing for normal command completion.
